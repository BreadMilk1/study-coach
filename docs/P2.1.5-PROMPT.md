## 3. P2.1-⑤ 设计决策（已定）

### 架构
- **Planner + Reviewer 双节点**一次交付（ARCHITECTURE.md 原设计，不拆）
- **2 tools**: `update_study_plan` + `generate_mindmap`

### Orchestration 策略
- **Planner: Deterministic** (跟 QuizMaster 一致)
  - 固定编排: 解析用户消息 → 调 LLM 生成 milestones JSON → `update_study_plan` 持久化 → `generate_mindmap` 生成 mermaid → 返回格式化输出
  - LLM tool-calling 推到 P2.2/P3 ablation
- **Reviewer**: 待定（看下一个设计问题）

### 设计原则（延续 P2.1-④ 模式）
- Tool 函数独立、接口干净、stateless（repo 显式传入）
- Planner node 用 `_safe_writer()` 包裹 `get_stream_writer()`（兼容单元测试直接调用）
- Judge rubric 复用 `judge_response(dimensions=None)` 参数化模式
- Plan-specific rubric 与 tutor/quiz rubric 无维度重叠
- Config-injection 模式延伸（planner/reviewer 通过 `config.configurable` 注入）

## 4. 待定设计问题

### Q1: Planner 核心行为？
- **A) 纯生成** — 调 LLM 生成 milestone 列表，持久化，展示。用户手动勾选 done。Reviewer 只做进度审查。
- **B) 生成 + 自适应调整** — 首次生成 plan。后续 check-in 时重新评估 mastery + mistakes，调 LLM 更新 milestones。Reviewer 做质量把关。

### Q2: `generate_mindmap` 触发时机？
- **A) 每次 plan 生成/更新后自动调用** — Planner 调 LLM 生成 plan → 再调 LLM 生成 mindmap → 一起返回
- **B) 用户显式触发** — 独立 keyword（「画脑图」「mindmap on X」），不耦合 plan 生成

### Q3: Reviewer 审查什么？
- **A) 审查 plan 质量**（类似 Judge 审查 tutor answer）— rubric 针对 milestone 合理性、粒度、时间安排
- **B) 审查 plan 执行进度** — 读 DB 里程碑完成情况，产出 overdue 警告 + 下一步建议
- **C) 两者都做** — GENERATE 时审质量，CHECK-IN 时审进度

### Q4: Plan 路径的多轮交互？
- Plan 生成后是否像 Quiz 一样设 `active_plan_id` 状态标记？
- 用户后续消息「把第三章拆成两节」是否路由到 Planner 做增量更新？
